## 2. 최종 평가 자료의 역할

1. 이 bag 전체와 파생 이미지·crop·라벨을 최종 평가 전용으로 둔다. 좌우 카메라와 인접 프레임은 같은 주행에 속한다.
2. 학습, hard-example mining, pseudo-label 학습, threshold 선택, 증강 범위 선택, BN 통계 갱신, self-supervised adaptation, teacher 학습에 사용하지 않는다. 라벨 없는 영상도 이 경계를 따른다.
3. 모델 개발 중에는 reader의 인코딩·좌표·타임스탬프를 기술적으로 확인할 수 있다. 장면별 모델 오류를 보고 후보를 다시 고르는 반복은 최종 평가에 해당하지 않는다.
4. 최종 후보의 가중치, 후처리, SignalAttr, threshold, 카메라 전처리, 측정 지표를 개발 자료에서 확정한 뒤 bag을 평가한다. baseline도 같은 시점에 같은 절차로 평가한다.
5. 최종 bag 결과로 후보의 채택을 거절할 수 있다. 결과를 보고 재설계하면 이 bag은 이후 **현장 회귀 기준 자료**가 되며, 독립 최종 일반화 주장을 위해 다른 주행을 확보한다.
6. 단일 3분 12초 주행은 그 장소·날씨·카메라 조건의 평가다. 야간·우천·희귀 상태가 없으면 해당 성능은 미측정으로 남긴다.

기존 AIHub validation은 이미 모델 선택과 사례 확인에 사용됐다. 개발 검증 자료로 계속 사용하고, 독립적인 실차 일반화 증거로 표현하지 않는다.

## 3. 입력과 좌표 계약

### 3.1 영상 식별과 읽기

- 정확도 평가는 각 카메라의 전체 영상 시퀀스를 독립적으로 처리한다. 좌우 메시지를 zip하거나 부족한 프레임을 복제하지 않는다.
- 이미지 키는 bag 내 파일 식별, 토픽, 저장 timestamp로 연결한다. timestamp 중복이 실제로 있으면 해당 토픽의 원본 메시지 순번을 추가한다. header timestamp는 시간 분석용으로 함께 보존한다.
- JPEG bytes를 RGB로 디코딩하고 현재 letterbox_focused_image를 사용한다. 이 bag의 800×600은 현재 입력 800×608에서 크기 변경 없이 상하 padding이 들어간다. 최종 박스·점열은 원본 800×600 좌표로 돌린다.
- OpenCV를 사용하는 구현은 BGR→RGB 변환을 입력 경계에서 한 번 한다. RGB/BGR, letterbox scale, padding을 실제 알려진 좌표로 확인한다.
- raw 영상에 붙은 CameraInfo만으로 이미 rectification됐다고 가정하지 않는다. 기본 평가는 기록된 raw 픽셀 그대로 한다. rectification을 비교하려면 별도 개발 자료에서 후보를 확정하고 영상과 GT를 같은 변환으로 옮긴다.
- 노드 재생은 필요하지 않다. 구현된 tools/predict_pv26_mcap.py는 rosbag2_py로 카메라 토픽을 읽고 기존 FocusedPerception에 연결한다. 최종 bag 전체 평가는 라벨과 후보를 확정한 후 사용한다.

독립 카메라 인지에는 stereo 동기화가 필요 없다. batch 2 처리시간 실험에서는 두 영상의 실제 timestamp를 보존하고 pairing 대기시간을 별도 측정한다. 미래 프레임을 미리 읽은 오프라인 배치를 실시간 지연으로 보고하지 않는다. 좌우 객체를 융합하지 않은 상태에서는 양쪽에 보이는 같은 신호등을 독립 관측으로 보고한다.

### 3.2 모델과 후단 경계

PV26 입력은 카메라 RGB다. GNSS·IMU·차량 상태는 상황 분류와 시간 분석에만 사용한다. 운전자 조향값, 차량 궤적, 과거 인지 노드 출력은 차선·신호등 정답이 아니다.

공개 출력은 [PRD](0_PRD.md)와 [추론 경로](../model/engine/inference.py)를 따른다.

- 신호등: vehicle_signal / pedestrian_signal 박스와 검출 신뢰도.
- 상태: 빨강·노랑·원형 초록 및 차량 좌회전, state_valid. 여러 등이 동시에 켜지는 허용 조합을 유지한다.
- 도로표식: white_lane / yellow_lane / stop_line의 원본 픽셀 점열과 신뢰도.
- 어느 신호등이 내 차로를 지배하는지, IPM 후 미터 좌표, 정지 결정, 주행 제어는 이번 모델 비교의 출력 범위에 포함하지 않는다.

## 4. 정답 라벨 작성

### 4.1 표본 구성

최종 추론은 전체 11,492장에 수행한다. 수동 정량 라벨은 다음의 **사전 표집 규칙**을 제안한다.

tools/prepare_pv26_mcap_labels.py가 0.5초 격자에 가장 가까운 좌우 프레임을 모델 예측 없이 추출하고 frames.jsonl에 원본 프레임 키를 남긴다. --event-windows로 수동 선정한 구간을 JSONL로 전달하면 해당 구간의 모든 카메라 프레임도 포함하고 중복 프레임은 한 번만 저장한다. 개발용 9월 19일 기록의 JPEG 12장으로 격자·이벤트 중복 제거를 확인했다. 지정 최종 bag의 전체 이미지 추출은 아직 하지 않았다.

| 층 | 선택 방법 | 역할 |
| --- | --- | --- |
| 공통 정적 평가 | bag 시작 기준 0.5초 간격의 시간 격자에 가장 가까운 각 카메라 프레임, 중복 선택 제외 | 자연 주행 분포의 박스·선분 평가. 약 384장/카메라 예상; 실제 수가 계약은 아님 |
| 신호등 이벤트 | 사람이 원본을 보고 정한 등장·가림·상태 변화·퇴장 구간의 전 프레임 | 상태 전환 지연, 연속 누락, 잘못된 상태 지속시간 |
| 차선 연속 구간 | 원본에서 정한 곡선·가림·교차로 등 연속 구간 | 프레임 간 흔들림·단절 확인 |
| 전체 재생 | 모든 영상 | 출력·decode 누락 수, 전체 지연 및 qualitative overlay |

0.5초 간격은 주석 비용을 줄이는 초기 설계값이며 정확도 합격 기준이 아니다. 이벤트와 연속 구간은 모델별 예측을 보지 않고 정한다. 공통 표본과 이벤트 표본의 점수는 따로 보고하며, 같은 프레임을 두 번 세어 전체 점수를 만들지 않는다. 이벤트 수가 적으면 30Hz 프레임 수로 독립 사례 수를 부풀리지 않는다.

라벨은 모델 예측으로 자동 확정하지 않는다. 보조 도구로 초기 주석을 만들더라도 사람이 원본을 보고 수정하고 확정한다. 모델 평가를 수행하는 개발자에게 최종 라벨과 오류 사례가 조기에 피드백되지 않도록 학습 입력과 별도 위치에서 관리한다. 모델 종류별로 GT를 바꾸지 않는다.

### 4.2 차선·정지선

- 도색 중심을 원본 픽셀 좌표로 표시하고 흰 차선·노란 차선·정지선을 구분한다.
- 평가 단위는 **동일한 도로표식 중심선을 나타내는 polyline 객체**이며 현재 AIHub의 의미와 맞춘다. 같은 점선을 페인트 조각마다 무조건 별도 객체로 쪼개지 않는다. 가림·갈라짐·교차점은 표시하고 서로 다른 차선을 하나로 묶지 않는다.
- 가려진 위치는 선을 상상해서 확정하지 않는다. 진짜 비관측 영역은 ignore 영역으로 두고, 예측과 GT 양쪽에 같은 영역 처리를 적용한다. 단순히 라벨링을 빼먹은 곳을 ignore로 바꾸지 않는다.
- 점선의 규칙적인 공백을 연결했다는 이유만으로 오검출 처리하지 않는다. 실제 AIHub 표본 14533456의 dotted polyline은 긴 중심선으로 주석돼 있고 현행 _roadmark_maps도 그 점들을 연속 raster로 그린다. 관측으로 같은 차선임을 확인할 수 있는 범위의 중심선과, 근거 없이 다른 선·차로·분기를 연결하는 오류를 구분한다.
- 기존 AIHub의 annotation polyline 단위와 분할 방식이 다르면 dataset별 점수를 별도로 보고한다. 새 MCAP 규칙을 이유로 과거 AIHub 기준선 지표를 재해석하지 않는다.
- 횡단보도·화살표·도로 균열·차량 경계는 차선·정지선 positive가 아니다. 라벨 범위 안의 오검출로 센다.
- 시간 평가가 필요한 구간에만 같은 물리적 도색의 track ID를 부여한다. 전체 정적 라벨에 불필요한 tracking 정보를 강제하지 않는다.

### 4.3 신호등

- 평가 가능한 모든 차량용·보행자용 신호등의 박스를 표시한다. 작거나 상태를 읽을 수 없다는 이유로 박스 검출 GT에서 제외하지 않는다. 객체 존재 자체가 불명확하면 ignore와 이유를 남긴다.
- 박스 종류와 점등 상태의 유효성은 따로 기록한다. 판독 불가 상태를 off나 green으로 대체하지 않는다.
- 차량: base color와 left_arrow의 조합. 보행자: red / green / off 또는 unreadable; 좌회전은 해당 없음.
- 실제 소등과 노출·반사·LED flicker로 판독할 수 없는 상태를 구분한다. 여러 원형 색이 동시에 켜져 제품 상태 정의로 표현되지 않는 경우는 state invalid로 남기고 검출 평가는 유지한다.
- 우회전 등 현재 제품이 지원하지 않는 화살표를 좌회전 positive로 쓰지 않는다.
- 이벤트 구간에는 객체 track ID, 상태 전환 시각의 관측 가능한 범위, 가림 구간을 표시한다. 한 카메라에서 관측 불가능한 순간을 다른 카메라의 라벨로 억지 채우지 않는다.

보존할 정보는 원본 프레임 키·크기, 실제 주석·ignore 영역, 상태 유효성, 필요한 이벤트 시간이다. 포맷의 무관한 추가 필드나 파일 개수로 평가를 거부하는 별도 validator는 만들지 않는다.

### 4.4 구현된 JSONL 연결 형식

tools/predict_pv26_mcap.py는 카메라별 원본 메시지 순번을 0부터 매기고 bag_time_ns, header_time_ns, bag의 절대 경로, PV26 관측을 한 줄씩 쓴다. 현재 tools/evaluate_pv26_mcap.py의 GT JSONL은 **주석이 완성된 프레임마다 한 줄**을 받는다. 아래는 형식 예시이며 실제 이 MCAP의 라벨이 아니다.

~~~json
{"bag":"/실제/기록/record_0.mcap","camera":"left","bag_time_ns":1234567890000000000,"topic_sequence":15,"signals":[{"class_name":"vehicle_signal","bbox_xyxy":[50,20,64,56],"state_valid":true,"base_color":"red","left_arrow":false}],"roadmarks":[{"class_name":"white_lane","points_xy":[[180,350],[200,280],[220,210]]}],"ignore_regions":[]}
~~~

signals와 roadmarks는 해당 프레임에서 모든 대상의 배열이며, 대상이 없으면 빈 배열이다. 상태를 읽을 수 없는 실제 신호등은 박스를 남기고 state_valid=false로 기록한다. 추가 필드는 허용하며 평가기가 쓰는 필드만 요구한다. bag 경로, 카메라, bag_time_ns와 topic_sequence의 조합으로 예측과 GT를 연결한다. header timestamp는 별도 시간 분석에서 쓴다.

이벤트 시간 목록은 bag timestamp 기준 start_ns와 end_ns를 사용한다. 이 값은 카메라 header 시각이나 사람이 읽는 날짜 문자열과 섞지 않는다. 예시: {"start_ns":1234567890000000000,"end_ns":1234567892000000000}. 이 도구의 출력 frames.jsonl은 **주석 위치 목록**이며, 신호등·차선 정답이 없는 상태에서 GT 파일로 이름만 바꿔 평가하지 않는다.

현재 scorer는 ignore_regions가 비어 있지 않은 프레임을 **통째로 정량 점수에서 제외**하고 수를 보고한다. 아직 부분 영역을 잘라 한 프레임의 다른 유효 라벨만 평가하는 기능은 없다. 중요한 교차로·가림 프레임이 많이 제외된다면 최종 점수를 확정하기 전에 이 계약을 구현해야 한다. 이미 작성된 최종 라벨의 일부만 조용히 사용한 결과를 전체 정확도라고 부르지 않는다.

## 5. 평가 지표

### 5.1 차선과 정지선

1. **기존 선분 F1/P/R 유지:** 클래스별 일대일 매칭과 symmetric mean nearest-point distance를 [geometry_metrics.py](../model/engine/geometry_metrics.py)에서 재사용한다. 기본 tolerance는 원본 8px다. 이 값은 현행 평가 설정이지 실차 허용 오차나 안전 합격선이 아니다.
2. **허용 오차 민감도:** 4 / 8 / 12px 결과를 함께 제안한다. 이 bag에서 output stride가 원본 4px이므로 1 / 2 / 3 grid-cell 규모의 오차를 구분하기 위한 것이다. threshold를 최종 bag에 맞춰 고르지 않는다.
3. **위치·coverage:** 매칭된 선의 위치 오차 중앙값·p95, GT/pred coverage, 그리고 미검출 GT도 분모에 포함하는 전체 GT 길이 coverage를 보고한다. 현재 mean_distance_px와 coverage는 매칭 성공 표본만의 평균이므로 누락률을 대신하지 못한다.
4. **구조 오류:** 단절·중복·다른 선으로의 연결·횡단보도/도로 경계 오검출 사례와 원시 개수를 함께 기록한다. 단순 출력 선 개수 감소를 개선으로 간주하지 않는다.
5. **정지선:** F1/P/R, 위치 오차, 양끝 방향의 180도 동치성을 반영한 각도 오차. 매칭 성공 표본의 각도만 좋아지고 recall이 떨어지는 경우를 분리한다.

AIHub 원본 1280폭과 MCAP 800폭은 8px의 상대적 크기가 다르다. 데이터셋 간 숫자를 직접 비교해 도메인 격차의 크기라고 단정하지 않는다. 원본 pixel과 이미지 폭으로 정규화한 오차를 함께 기록한다.

**자글거림 진단:** 같은 GT를 기준으로 일정 arc-length 간격에서 예측의 법선 방향 위치 잔차 e(s)를 얻고, 인접 잔차의 2차 차분 크기를 비교한다. 원래 도로의 곡률을 지우는 모델에 보상을 주지 않기 위해 예측 좌표 자체의 곡률을 최소화하는 지표로 바꾸지 않는다. 동일 sampling 간격, 매칭 및 visibility 규칙을 적용하고 F1·coverage·위치 오차와 함께 해석한다. smoothing으로 점 수나 선 길이를 줄여 얻은 개선은 인정하지 않는다.

**시간 안정성:** 추적 라벨이 있는 동일 도색에서 GT 움직임을 뺀 위치 잔차의 프레임 간 변화, 검출 중단 시간, 잘못된 연결 지속시간을 측정한다. 카메라가 움직이는 원본 좌표의 차이를 그대로 jitter라고 부르지 않는다. 대응을 만들 수 없는 구간은 미측정으로 표시한다. 이 항목은 신규 구현이 필요하다.

### 5.2 신호등 검출과 상태

| 평가 단계 | 입력 / 고정 조건 | 보고할 결과 |
| --- | --- | --- |
| 검출만 | PV26, 같은 confidence. 현행 비교 기준 0.25와 IoU 0.5 | 종류별 P/R/F1, TP/FP/FN, 박스 크기별 recall, 종류 혼동 |
| 상태 단독 | GT box를 동일 crop 정책으로 자른 RGB + SignalAttr | 상태별 P/R/F1, macro F1, 유효 판독 비율, 판독 불가·소등 혼동 |
| 연결 평가 | 예측 box + 같은 SignalAttr | GT에 매칭된 상태 성능, 전체 GT 분모의 end-to-end recall, 오검출 상태 |
| 시계열 평가 | 원래 timestamp 순서, causal 처리 | 등장 후 첫 검출 지연, 연속 누락 길이, 상태 전환 지연, 잘못된 green/좌회전 지속시간 |

검출을 성공한 crop에만 조건부 계산한 상태 정확도와 전체 파이프라인 성능을 섞지 않는다. 예측 박스가 없거나 state invalid면 end-to-end 유효 GT 상태 recall에서 누락이다. GT가 판독 불가인 프레임의 상태를 임의의 색으로 정답 처리하지 않는다.

특히 GT red인데 valid green 또는 valid left_arrow를 출력하는 오류, red 누락, green↔left_arrow 혼동을 별도로 센다. 이것은 관측 상태의 오류이며 주행 허가 판정 자체가 아니다. 원래 red+left_arrow인 허용 조합을 false-arrow로 세지 않는다.

양성이 없는 클래스는 support=0과 함께 N/A로 표시한다. FP가 있다면 그 수와 precision 해석은 남긴다. 드문 상태의 프레임이 많더라도 동일 신호등의 한 이벤트면 독립 이벤트는 하나다.

PR curve나 AP50:95를 추가할 경우 score를 평가기에 전달해 집계한다. 현재 evaluate_focused는 고정 confidence의 F1이 중심이므로 AP가 이미 구현됐다고 가정하지 않는다. 운영 threshold는 개발 검증에서 정하고 최종 bag에서는 변경하지 않는다.

## 6. 시간·자원 평가

[PRD](0_PRD.md)의 RTX 4060, 좌우 각각 800×600 입력 30Hz, 카메라별 출력 목표 20Hz·하한 10Hz, 좌우 33ms 미만 지향을 유지한다. 20Hz와 10Hz의 주기는 각각 50ms와 100ms다.

- cold start, warm batch-2 전처리→PV26→선 후처리→SignalAttr, JPEG decode, 카메라 큐 대기, 전체 결과 나이(age)를 구분한다.
- 평균·중앙값·p95·p99, 실제 출력 Hz, drop/skip 수, peak VRAM을 측정한다.
- offline 원본 전체 처리량과 timestamp 간격을 따라 공급하는 실시간 모사 결과를 구분한다.
- 포화 시 밀린 모든 프레임을 늦게 처리할지 최신 프레임을 선택할지는 최종 소비자의 기존 정책을 따른다. 이 연구가 임의로 런타임 drop 정책을 바꾸지 않는다.
- 선을 지나치게 버려 후처리가 빨라진 후보는 정확도 손실과 함께 보고한다.
- 후단 및 20Hz LiDAR와의 동시 실행은 마지막 운영 성능 검증 항목이다. bag 단독 측정으로 그 결과를 대신하지 않는다.
- 물리 차량 조작 없이 오프라인 처리한다. 로컬 ROS 재생이 실제로 필요해지는 별도 작업에서는 차량 명령 토픽과 장치에 연결하지 않는 실행 경계를 먼저 확정한다.

## 7. 비교·판정

기준 본체는 80,000 step latest.pt다. SignalAttr는 제품 의미를 학습한 개발 검증 승자를 먼저 정하고 기준 본체와 최종 후보에 **같은 가중치·정책**을 붙인다. SignalAttr 자체의 변경 효과는 같은 검출기에서 별도로 비교한 뒤 최종 조합을 보고한다.

개발 검증에서 미리 고른 후보만 평가한다. 신호등 성능을 희생해 차선 점수가 올라간 모델을 채택하지 않는 PRD를 따른다. 차선·상태·지연의 모든 개선을 하나의 평균값으로 상쇄하지 않는다.

차이의 신뢰구간은 같은 카메라·같은 주행 구간에 대한 paired 비교로 계산한다. 인접 프레임을 독립 표본으로 bootstrap하지 않는다. 사람의 장면/이벤트 단위 또는 시계열 자기상관을 반영한 block 단위로 묶는다. 한 bag 안의 신뢰구간은 다른 날·장소 일반화의 신뢰구간이 아니다.

정확도 비열등 허용폭이나 false-green 허용률은 현재 PRD에서 수치로 정해져 있지 않다. 따라서 새로운 허용 손실을 발명하지 않는다. 명확한 신호등 악화는 채택 대상에서 제외하고, 차이가 불확실하면 근거 불충분으로 남긴다. 모든 후보가 악화하면 기존 기준 모델을 유지한다. 이 문서의 연구 판정은 차량 배포 승인과 다르다.

## 8. 다음 실행자의 산출물과 저장

- 원본 위치를 유지하고, 산출물은 기존 bag에 덮어쓰지 않는다.
- prepare_pv26_mcap_labels.py는 JPEG bytes를 재인코딩하지 않고 저장하고, 완료된 frames.jsonl을 마지막에 공개한다. 실제 원본 기준 전체 추출은 외장 저장소 확인 후 진행한다.
- 기준 경로는 /home/kai/yolopv26/runs/<experiment>/evaluation/260920_140738/ 이다. 사용자가 kai 환경에서는 이 저장소의 runs를 산출물 경로로 지정했다. 긴 실행 전 여유 공간을 확인하고 원본 기록 디렉터리에 산출물을 쓰지 않는다.
- 디스크가 준비되면 필요한 라벨 프레임·crop만 materialize하고 전체 영상은 MCAP에서 streaming한다. CPU decode는 순서가 보존되는 bounded worker queue를 사용할 수 있다. GPU 모델별 실행은 같은 장치에서 직렬화해 지연 비교의 간섭을 줄인다.
- 결과는 기존 JSON/JSONL 관측, 클래스별 지표, 비교 표, 대표 overlay와 전환 이벤트 영상으로 충분하다. 새 검증 프레임워크·readiness gate·소스 hash 체계는 필요 없다.
- 구현된 scorer는 박스 IoU 0.5, 기존 선분 매칭 tolerance 8px, GT 신호등 상태와 연결한 TP/FP/FN을 계산한다. GT box만 넣은 상태 단독 평가, ignore 영역 내부 부분 점수, 시계열 jitter·전환 지연 지표는 아직 추가해야 한다.
- 모델 예측 입력에는 GT를 전달하지 않는다. 평가기는 저장한 예측과 GT를 프레임 키로 결합한다. 입력 경계에서 필요한 좌표·라벨 유효성을 한 번 확인하고 내부 전달마다 재검사하지 않는다.
- 원본의 전체 해시를 매번 만들거나 모델 추론 전후에 파일을 다시 해시하지 않는다. 배포용 결과 승격에 별도 무결성 확인이 필요하면 그 시점의 한 번의 작업으로 다룬다.

이 문서의 완료 범위는 기록 구조·시간 특성 확인과 평가 설계다. **최종 라벨, MCAP 모델 예측, 정량 성능, 영상 안정성, RTX 4060 동시 실행 지연은 다음 실행자의 작업**이다.
